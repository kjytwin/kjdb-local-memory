# 업데이트·백업·복원

데이터의 기본 위치는 `%LOCALAPPDATA%\KJDB\stores\<프로젝트 ID>`이다.
`--data-root`를 지정했다면 그 경로 아래 프로젝트 폴더를 사용한다.
패키지 폴더와 데이터 폴더는 서로 다르다.

## 업데이트

1. 해당 프로젝트를 사용하는 모든 앱과 KJDB 서버를 완전히 종료한다.
   파일이 사용 중이면 강제 복사하거나 잠금을 해제하지 않는다.
2. 프로젝트 데이터 폴더 전체와 앱의 기존 MCP 설정을 새 백업 폴더에 복사한다.
   백업은 개인정보를 포함할 수 있으므로 공개 저장소에 올리지 않는다.
   원본과 복사본 `memory.log`의 `Get-FileHash -Algorithm SHA256` 결과가 같은지 확인한다.
3. 새 ZIP을 새 폴더에 풀고 릴리스의 SHA256을 확인한다. 기존 패키지를 덮어쓰지 않는다.
4. 앱 설정의 KJDB 실행 파일·스크립트 경로만 새 패키지로 바꾼다.
   프로젝트 ID와 데이터 경로, 다른 MCP 서버 설정은 유지한다.
5. 앱을 하나만 시작하고 기존 메모리의 UUID와 본문을 get으로 확인한다.
   새 메모리를 저장한 다음 앱을 완전히 재시작하여 다시 조회한다.

읽기만 수행한 경우 데이터 파일이 바뀌지 않는지와, 새 버전이 기록한 데이터를
미리보기에서 다시 읽을 수 있는지는 출시 검사에 포함한다. 이 결과를 미래의 모든
버전에 대한 호환성 보장으로 해석하지 않는다. 버전별 출시 기록을 확인한다.

## 이전 버전으로 돌아가기

모든 관련 앱과 서버를 종료한 뒤 MCP 실행 경로를 보존한 이전 패키지로 바꾼다.
해당 버전 조합의 재열기 검증이 없다면 원본 데이터에 바로 연결하지 말고 복사본에서
확인한다. 업데이트 전 상태로 돌아가려면 아래 백업 복원을 사용한다.

## 백업 복원과 손상 대응

1. 앱과 서버를 종료한다. 현재 데이터 폴더를 날짜가 붙은 별도 위치에 보존한다.
   손상되었다고 판단한 파일도 삭제하거나 덮어쓰지 않는다.
2. 백업을 비어 있는 새 데이터 루트의 동일 프로젝트 ID 폴더에 복사한다.
   복사한 `memory.log`의 SHA256이 백업과 일치하는지 확인한다.
3. 설정 생성기의 `--data-root`로 새 루트를 지정한다. 앱을 하나만 열어 기존 UUID를
   조회하고 복원 시점의 본문을 확인한다. 복원 이후의 변경은 백업에 포함되지 않는다.

정상 백업이 없으면 손상된 원본을 초기화하거나 반복 기록하지 않는다. 오류와 파일을
보존해 조사한다. 임의 파일 자르기, 로그 병합, 자동 복구는 지원 절차가 아니다.
실행 중 백업이 필요한 개발자는 native `MemoryStore.backup`을 사용할 수 있지만
이는 신뢰할 수 있는 운영자 API이며 AI 도구로 노출하지 않는다.
